# Products catalogue: category tree, spec tables, search (McMaster-Carr style)

Date: 2026-10-14 · Status: **draft for owner review** · Repo: `brandonr2630/q2m-website` · Branch: `docs/products-catalogue-spec`

Supersedes the "one hub + one page per line" structure in `2026-10-13-products-ocr-reducers-design.md` (§3-4, §8 "no filters or search"). Everything else in that spec (own wording, no OCR logo/photos/tables until permitted, no prices, no `Product`/`Offer` schema, authorised-agent wording) still holds.

Items marked **[ASSUMPTION]** were not stated by the owner and need a yes/no. Items marked **[DECISION]** are proposals made here with a reason; the owner can overrule them. Section 14 lists the open questions.

## 1. Goal and understanding

**Goal.** Make the Products section able to carry many product lines without becoming a long page or a wall of cards. Today it has one line (OCR RP Series shaft-mounted gear reducers): a hub plus one page, in 5 languages (en/es/pt/nl/fr), generated by `scripts/build-product-pages.js` and checked by `scripts/verify-products.js` (0 failed at ship time).

**What the owner chose** (in chat, 2026-10-14):

- Model it on McMaster-Carr: a category tree with drill-down, spec tables with filters, and a search box; plain, dense, text-first, fast.
- Purpose: scale to many product lines.
- A category with no spec data stays hidden until populated.
- The OCR gear-reducer spec table and images will be supplied by the owner later.

**Success looks like:**

1. A buyer can reach any model in at most three clicks from `/products/`, or in one search.
2. Adding a product line is a data change (plus a run of `npm run build-all`), with no template or script edits.
3. Every populated page is static, crawlable HTML in 5 languages; filters and search are enhancements, not requirements.
4. No page is slower than today's equivalent; accessibility no worse than the current site (home Lighthouse a11y 96).
5. The enquiry route stays the existing contact form. No cart, no prices, no accounts.

**Out of scope:** cart, prices ("price on request" stays), accounts, OCR logo/photos/rating table until supplied and permitted, conveyors and concrete content (the owner's `q2m-products.md` taxonomy exists but has no real rows yet), pump-curves feature, interchangeability appendix.

## 2. Approach (chosen)

Static category pages generated from one data file, plus small vanilla JS for filtering and search. No backend, no JS-only content.

Alternatives considered and rejected:

| Option | Why not |
|--------|---------|
| One client-rendered catalogue page (fetch JSON, render in JS) | Googlebot sees an empty shell; the site's own lesson 5 ("content that must be indexed should be inline"). Breaks the no-JS case. |
| Third-party catalogue/e-commerce platform | Adds a host, a script and likely cookies/analytics; the privacy page promises none. Overkill without a cart. |
| Keep hand-written content file per line (today's `PAGES` array) | Works for 1-3 lines. Does not give a tree, tables or search without editing build code per line. |

## 3. Information architecture

### 3.1 Tree

A tree of nodes. A node is a **category** (has children) or a **family** (leaf: a product family with copy and, later, a spec table). Depth is not capped, but the owner's taxonomy already reaches 4 levels (e.g. Conveyors & Bulk Handling › Hardware › Pulleys › Head Pulleys), so the templates must handle 1-5 levels.

At launch, one branch: **Gear Reducers → OCR RP Series**. Nothing else is shown.

### 3.2 Populated-only rule (owner decision)

A node is **published** when it is a family with real data, or a category with at least one published descendant. Real data means a spec table with at least one row, or, for the OCR page until the table arrives, the verified-fact copy already live (facts strip, construction, applications, FAQ). The rule is derived by the build, not set by a flag, so adding rows is the only act that makes a node appear.

Unpublished nodes are absent from: the tree, the hub list, breadcrumbs, the search index, `sitemap.xml`, `llms.txt` / `llms-full.txt` and the nav. They produce no HTML file. The owner's conveyors and concrete groups can sit in the data file as empty nodes (or not be entered at all) with no effect. `verify-products.js` fails if an unpublished node leaks into any of those places.

A category with exactly one published child still gets its own page (it is a breadcrumb target and a valid URL). It is thin at launch ("Gear Reducers" lists one family). **[DECISION]** Accept this, give each category a one-paragraph intro, and review once a second family exists. Listed under risks.

### 3.3 URL scheme **[DECISION]**

`/products/<category>/<family>/` as a directory with `index.html`, deeper for deeper trees: `/products/gear-reducers/ocr-rp-series/`, later e.g. `/products/conveyors-and-bulk-handling/hardware/pulleys/head-pulleys/`.

- Slugs are English in every language, as today (language variants live under `/es/`, `/pt/`, `/nl/`, `/fr/` with the same path). Display names are translated; slugs are not.
- Directory-style matches the existing hub (`/products/`) and the planned breadcrumbs, and keeps the URL stable if a family later gets child pages.
- Reason against a flat scheme (`/products/<slug>.html`, what exists now): it cannot express the tree, so breadcrumbs, the tree highlight and a "section" URL would all be fake. Reason for it: zero migration.

**Existing OCR URLs.** `/products/ocr-rp-series-shaft-mounted-gear-reducers.html` and its 4 language copies shipped on 2026-10-13, so they may be indexed (Search Console has not been checked for them). Plan: **301 each old URL to its new directory URL** with `RedirectMatch 301` lines in `.htaccess`, update every internal link, the sitemap, hreflang sets and `llms*.txt` to the new URLs, and keep the redirects permanently. Reason: the old page was live about one day, so little ranking is at stake, and a 301 transfers what exists. `.htaccess` is site-wide and a syntax error 500s everything (handoff lesson 11), so the change is small, inside the existing file, and verified live with `curl -I` on the 5 old URLs (expect 301 and the right `Location`), on the 5 new URLs (expect 200), and on `/`, `/depot.html`, `/about.html` (unchanged). If the owner would rather avoid touching `.htaccess`, the fallback is to keep the old filename as the canonical URL of that one family, at the cost of an inconsistent scheme. Fallback is not recommended.

### 3.4 Pages generated

| Page type | URL example | Content |
|-----------|-------------|---------|
| Hub | `/products/` | Search box, tree, list of top-level categories (name, one line, count of families beneath). |
| Category | `/products/gear-reducers/` | Search box, tree (expanded to here), breadcrumb, intro, list of children (name, one line, image thumb if any). |
| Family | `/products/gear-reducers/ocr-rp-series/` | Breadcrumb, H1, one-line description, image strip, spec table with filters, existing copy sections, FAQ, CTA. |

Every page exists in 5 languages with a full hreflang set and `x-default`.

### 3.5 Breadcrumbs and schema

Visible breadcrumb `Home › Products › Gear Reducers › OCR RP Series` on every Products page (handoff §2 deferred this; the tree makes it necessary). Each crumb is a link except the last. `BreadcrumbList` JSON-LD matches the visible trail exactly.

- Hub and category pages: `CollectionPage` + `ItemList` (children) + `BreadcrumbList`.
- Family pages: `WebPage` + `Brand` + `BreadcrumbList` + `FAQPage` (as now). The spec table is **not** marked up as `Product` or `Offer` (handoff lesson 7: no price, so invalid). Plain `ItemList` of model names is allowed but optional; it is not needed for launch.
- The existing nodes `#organization` and `#website` are referenced, not redefined.

## 4. Data model

One file: `scripts/products-data.js` (CommonJS, like `product-pages-content.js`). **[DECISION]** JS rather than JSON so wording can use template literals and comments; the build and the search-index writer both `require` it.

```js
// Illustrative shape, not final code
NODES = [
  { id: 'gear-reducers', parent: null, slug: 'gear-reducers',
    name: { en: 'Gear Reducers', es: '…', pt: '…', nl: '…', fr: '…' },
    description: { en: '…', /* 5 langs, ≤160 chars: used as meta description and list text */ },
    intro: { /* 5 langs, one paragraph, category pages only */ },
    order: 10 },
  { id: 'ocr-rp-series', parent: 'gear-reducers', slug: 'ocr-rp-series',
    brand: { name: 'O.C.R. Riduttori', url: 'https://www.ocr-riduttori.com' },
    serviceParam: 'reducers',
    name, description, title, lead, h1Html,           // per language, as today
    facts, how, build, apps, support, faq,            // migrated from product-pages-content.js
    images: [ { file: 'assets/products/ocr-rp/rp-85.webp', jpg: '…jpg', w, h, alt: { /* 5 langs */ } } ],
    specs: {
      columns: [
        { key: 'model',  type: 'text',   label: { /* 5 langs */ }, unit: null, sticky: true, search: true },
        { key: 'size',   type: 'enum',   label: {…}, unit: null,  filter: 'select' },
        { key: 'ratio',  type: 'number', label: {…}, unit: null,  filter: 'range' },
        { key: 'kw',     type: 'number', label: {…}, unit: 'kW',  filter: 'range' },
        { key: 'torque', type: 'number', label: {…}, unit: 'Nm',  filter: 'range' },
      ],
      rows: [ { id: 'RP-85-4', model: 'RP 85', size: '85', ratio: 4, kw: 0.6, torque: 160 }, … ],
    },
  },
]
```

Rules enforced by the build (build fails with a message naming the node and field):

- Every `name`, `description`, column `label` and image `alt` has all 5 languages, non-empty.
- `description` ≤ 160 characters (existing `MAX_DESC`).
- Slugs are unique among siblings, lowercase, `[a-z0-9-]`.
- Every `parent` exists; no cycles.
- Row keys match declared columns; `number` columns hold numbers, `enum` values come from a list derived from the rows.
- Every row has a stable `id` (used by the enquiry link and the search index).
- Column `unit` strings are data (not translated) when they are SI symbols; if a unit needs words, it takes a per-language object.

**Migration.** The OCR copy in `PAGES[0]` of `product-pages-content.js` moves into the `ocr-rp-series` node unchanged (same wording, so the migration is a no-op diff in rendered text, which is a verifiable acceptance check). `HUB` text moves to the hub entry of the new file. `product-pages-content.js` is then deleted. Slugs and copy for new product lines follow the same pattern as OCR.

### 4.1 Spec-table import (never retype numbers)

The owner will send the OCR table as `.xlsx` or `.csv`. A new script `scripts/import-spec-table.js <node-id> <file>` reads it and writes `scripts/products-data/<node-id>-rows.js` (generated, committed), which `products-data.js` requires. Rules:

- The import maps spreadsheet headers to column keys through a small mapping object in the data file; unknown or missing headers fail with a list.
- Numbers are parsed, not stringified; decimal commas are rejected with a message rather than guessed.
- The script prints a row count and a diff against the previous rows (added/removed/changed), so the owner can sanity-check against the source.
- `.xlsx` reading uses a dev-only dependency in `scripts/package.json` (for example `xlsx` or `exceljs`), as `sharp` and `cheerio` already are. `scripts/` is not deployed.
- Row data is **facts from the OCR catalogue**. **[ASSUMPTION]** the owner has OCR's agreement to publish the rating table, as they said they will supply it; the build does not enforce this, but §13 lists it as an item to confirm in writing before the table goes live.

## 5. Visual direction

Applies `frontend-design` and `ui-ux-pro-max` guidance, bounded by the site's existing shell.

**Principle: a catalogue, not a brochure.** McMaster-Carr's value is density, scannability and speed. We borrow: text-first lists, fixed-width left tree, tables as the main content, almost no decoration, instant feedback. We do not copy its layout or look (own wording and design; the owner's brand is dark with gold).

**Tokens.** Use the existing page tokens (`--ink`, `--ink-2`, `--ink-3`, `--text`, `--text-2`, `--gold`, `--border`). No new palette.

- Body text `--text` (#F0F0F0) on `--ink` (#0A0A0A) and `--ink-3` (#1A1A1A): well above 4.5:1.
- Secondary text `--text-2` (#A0A0A0): about 7:1 on `--ink`, about 6:1 on `--ink-3` (to be measured with computed styles, not by eye; lesson 17).
- **`--text-3` (#505050) must not be used for any catalogue text** (about 2.5:1 on `--ink`). Disabled and placeholder text use `--text-2`.
- Gold (#F5C500) is for links on hover/active, the current tree node, focus rings and the result count, nothing decorative. Gold on `--ink` is above 12:1.

**Layout.**

- Desktop (≥ 900 px): two columns. Left rail 240 px (tree), content fills the rest, max line width unchanged from the rest of the site. The rail is sticky under the fixed nav so the tree stays reachable while scrolling a long table.
- Tablet/phone (< 900 px): the tree becomes a "Categories" disclosure (`<details>`) above the list, closed by default except on the hub where it is open. Search box stays visible above it.
- Lists of children: single-column, one row per child: name (link), one-line description, small chevron. Row height ≥ 44 px on touch (target size), 36-40 px on desktop pointers. 1 px `--border` between rows. No cards, no hover lift, no `reveal` entrance animations on catalogue pages (the existing `.svc-card` card pattern and its transform are not used here).
- Typography: existing Oswald for H1/H2 and the tree top level, Barlow Condensed for table headers, `font-variant-numeric: tabular-nums` on all numeric cells (the facts strip already does). Table cell text 14-15 px, header 12-13 px uppercase with letter-spacing, same scale as the rest of the site.
- Tables: zebra off; 1 px row rules; numeric columns right-aligned; units in the header (`kW`, `Nm`) not repeated per cell; hover highlights the row (background `--gold-dim`); sticky header row inside the scroll container; sticky first (model) column on phones.
- Motion: none except the existing focus and hover colour transitions; `prefers-reduced-motion` respected (nothing to remove).
- Images: strip of up to 4 thumbnails above the table, `<img>` with width/height set (no layout shift), `loading="lazy"` below the fold, WebP with JPG fallback via `<picture>`. No lightbox (the owner rejected click-to-enlarge on the About page, PR #91).

**Search box visuals.** Full-width input at the top of the content column, 48 px high, magnifier icon (inline SVG, `aria-hidden`), visible label (not placeholder-only), results in a panel directly below with three groups.

## 6. Navigation, tree and accessibility structure

- The tree is `<div class="cat-tree" role="navigation" aria-label="Product categories">` (not a `<nav>` element, which the global `nav { position: fixed; top: 0 }` CSS would pin; handoff lesson 1). Nested `<ul>`; the current page's link has `aria-current="page"`; ancestors are `<details open>` so the path is expanded without JS.
- The tree is rendered into every Products page in the static HTML (no JS). It lists only published nodes. Each language gets its own tree with translated names and language-prefixed hrefs.
- Breadcrumb is `<div class="crumbs" role="navigation" aria-label="Breadcrumb">` with an `<ol>`; the last item has `aria-current="page"`.
- Landmarks: one `<main>`; the tree and search are inside it as labelled regions.
- Keyboard: tree and breadcrumb are plain links and disclosures (tab order, Enter/Space); the search and filter controls are described in §8-§9.
- Skip link "Skip to products" before the tree on tablet and desktop is **not** added (the tree is short at launch); revisit when the tree exceeds ~30 links. **[DECISION]**

## 7. Family page

Top to bottom: breadcrumb, H1, one-line description, image strip (when images exist), the spec section (when rows exist), then the existing copy sections (how it works, construction, applications, support, FAQ), then the CTA. **[DECISION]** The table sits above the prose because for a catalogue the table is the product; the facts strip stays above everything as the summary.

### 7.1 Spec table

- The **full table is in the HTML**, one `<tr>` per row, so Googlebot and screen readers see every model with no JS.
- `<table>` with `<caption>` (visually hidden or shown, family name + "specifications"), `<thead>` with `<th scope="col">`, first cell of each row `<th scope="row">` (model).
- Each row carries `data-*` attributes for filtering (`data-size="85" data-ratio="4" data-kw="0.6" data-torque="160"`); the values are the same as the visible cells.
- Last cell of each row: **Request quote** link to `/?service=<serviceParam>&item=<row id>#contact` (language-prefixed on language pages), translated label.

### 7.2 Filters (progressive enhancement)

Rendered by JS from the table's own `data-*` and a small JSON block of column definitions embedded inline in the page (so no extra request). Without JS the filter row is not shown and the whole table is visible.

- `enum` columns: a native `<select>` ("All" + values).
- `number` columns: two native `<input type="number">` (min/max) with `inputmode="decimal"`, placeholders from the data's min and max.
- Each control has a visible `<label>` (the column header and unit).
- Result count line: `12 of 40 models` (translated; the strings take `{n}` and `{total}`), in a `role="status"` `aria-live="polite"` element so changes are announced once, debounced ~300 ms.
- **Clear filters** button, enabled only when a filter is active; resets all controls and the count.
- Rows are hidden with the `hidden` attribute (not `display:none` in CSS only), so assistive tech agrees with the screen.
- When no row matches: a visible "No models match these filters" row spanning the table plus the Clear button.
- Filter state is mirrored in the URL query (`?kw-min=5&size=105`) via `history.replaceState`, so a filtered view can be shared; on load the query is applied. Crawlers index the unfiltered page (canonical has no query). **[DECISION]** Included because it is about 8 lines and is how McMaster filters feel shareable; drop it if the owner wants less.
- Size: about 40-60 lines of inline vanilla JS, no library. Runs on `DOMContentLoaded`; no work on pages without a `.spec-table`.
- Phone: the filters sit in a `<details class="filters">` ("Filter models", with the active-filter count in the summary) above the table; the table scrolls horizontally inside a `div` with `overflow-x:auto` and `tabindex="0"` plus an accessible name, with the model column `position: sticky; left: 0` and an opaque background.
- Not in this release: sorting by clicking headers. **[DECISION]** Rows come in the data order (OCR's size/ratio order). Sorting is a small later addition if the owner asks; it is not needed to meet the stated goals.

### 7.3 CTA and enquiry prefill

The page CTA keeps `?service=reducers#contact`. Per-row links add `&item=<id>`.

**Check of `index.html`'s form handler** (done for this spec): the handler at `index.html` ~line 2303 reads only `?service=` and maps it through a fixed object to `#cf-service`; the form has name, email, company, phone, service select, message textarea, response method. There is no item field. **Feasible and small:** extend the same IIFE to read `item`, validate it (`^[A-Za-z0-9 ._/-]{1,60}$`), and, if `#cf-message` is empty, set its value to a short template ("Enquiry about OCR RP 85, ratio 4: "), leaving the cursor at the end. Because the language pages are generated from `index.html`, the change propagates through `build-lang-pages.js`. Two details:

- The template wording must exist in 5 languages (it is user-visible text in a field); it lives in the same `translations` object under a new key and is read after language is applied.
- It never auto-submits and never sets hidden fields; the user still reads and sends. No personal data in the URL (only a model id).

Risk: `index.html` and `build-lang-pages.js` are currently being edited in another worktree (`slideshow-img`, alt text). This change is therefore **scheduled after that work merges** (§12) and kept to the one IIFE and one translation key.

## 8. Search

### 8.1 Scope and placement **[DECISION]**

The search box appears at the top of `/products/` and on **every Products page** (hub, category, family). It is not added to the global nav.

Reason: the global nav is a fixed single row that already carries 6-7 labels plus the language flags, and the nl/fr labels are longer than English (handoff lesson 22 on width problems); adding a search field or icon changes the header on every page of every language and forces regeneration of all page types and their tests. A Products-only box covers the actual need (find a model or a category) at no cost to pages that have no catalogue. Re-evaluate when the catalogue has more than a few dozen families. The nav "Products" link already leads to the search.

### 8.2 Index

The build writes one small JSON per language: `/products/search-index.json` (en), `/es/products/search-index.json`, etc. **[DECISION]** same filename in each language directory, so the page needs no per-language filename logic.

Content: only published nodes. Three entry kinds:

```json
{ "c": [ { "n": "Gear Reducers", "u": "/products/gear-reducers/", "d": "…" } ],
  "p": [ { "n": "OCR RP Series Shaft-Mounted Gear Reducers", "u": "/products/gear-reducers/ocr-rp-series/", "d": "…", "k": "O.C.R. Riduttori OCR shaft mounted" } ],
  "m": [ { "n": "RP 85", "u": "/products/gear-reducers/ocr-rp-series/#RP-85-4", "p": "OCR RP Series", "s": "0.6 kW · 160 Nm" } ] }
```

- Categories (`c`): names and descriptions at every published category.
- Products (`p`): family name, description, brand and keywords.
- Models (`m`): one per spec row, with a short parenthetical spec summary. Row anchors `#<row id>` exist in the table (`<tr id="RP-85-4">`), so a model result opens the family page at that row (target row gets `:target` highlight).
- Size: today a few KB; a 40-row family adds about 2-3 KB gzipped. If a language index passes about 100 KB the plan should split models by family (loaded when searching within one). **[DECISION]** Not needed now; the check in §11 reports index size.

The index is generated by `build-product-pages.js` in the same run, so it can never be out of step with the pages.

### 8.3 Behaviour

- JS loads the language's JSON on **first focus** of the input (or first keystroke if focus was skipped), once, with `fetch`, cached by the browser. No request on page load, so nothing changes for first paint or LCP.
- Matching runs on each input event, in memory.
- Normalisation (applied to the query and to indexed strings): lowercase; fold diacritics (`é → e`, important for es/pt/fr); strip everything that is not a letter or digit for a second "squashed" form. A query matches an entry if every query token is a prefix of a word of the entry's name/keywords, **or** the squashed query is a substring of the squashed name. So `RP 50`, `rp50` and `RP-50` all find the model `RP-50`; `reduct` finds "Reductores"; `ocr` finds the OCR family and its models.
- Ranking: exact squashed-name match, then name-prefix, then word-prefix, then description match; ties by tree order. At most 5 per group, 12 in total.
- Results panel groups: **Categories**, **Products**, **Models** (headings translated; empty groups omitted).
- **Enter** opens the top result (or the first in the keyboard-focused item); **↑/↓** move through results; **Esc** closes the panel and returns focus to the input; mouse/touch select a result.
- Accessibility: input `role="combobox"` with `aria-expanded`, `aria-controls` the listbox, `aria-activedescendant` on the active option; results `role="listbox"`/`option`; a visually hidden `aria-live="polite"` region announces the count ("3 results", "No results"). Visible label above the input.
- No results state: "No match. Try a model number such as RP 85, or browse the categories." plus the link to the tree.
- **No-JS fallback:** the input sits in a `<form>`; without JS the form is hidden by a `.js .search` class toggle and replaced (inside `<noscript>`) by "Browse all categories" links to `/products/`. The tree is always there, so the page stays navigable.
- Fully client-side. No query is sent anywhere and nothing is logged or stored (not even `sessionStorage`).

### 8.4 Privacy check

`privacy.html` states "no cookies, analytics or advertising trackers" and says the only stored value is the `sessionStorage` flag `q2m-lang-redir` (checked in the file, `pv_s5_p`). The search and filters keep their state in memory and, for filters, in the URL query; they store nothing and call no third party. **No change to `privacy.html` is needed.** `verify-products.js` gets an offline check that Products pages and `products` scripts contain no `localStorage`, `document.cookie`, `fetch(` to a third-party origin, `gtag`, `analytics` or similar (the repo already has an offline check for trackers).

## 9. Internationalisation

- Every visible string belongs to a key with a value in all 5 languages (lessons 14, 16): tree headings, "Categories", breadcrumb label, search label/placeholder/status text, group headings, filter labels, "All", "Clear filters", "N of M models", "No models match", "Request quote", table caption, "Filter models". The new strings live in one `UI` object at the top of `products-data.js` (or its own `products-ui.js`), and the build bakes the text. The page JS reads its small string table from an inline JSON block per page, so the script itself has no language logic.
- Non-visible strings too (the site has a known gap here, handoff §4): `aria-label`s, image `alt`, `title`s, `<caption>`, `aria-live` messages are all in the same string table. The current English-only `aria-label="Menu"` on the shell stays an existing known issue, not this project's.
- Spec column headers and units come from the data (per-language labels).
- Number formatting: decimal separator **[DECISION]** stays a point in all languages on these pages (technical data; catalogue source uses points; avoids mixed formats in `data-*` values and input min/max). The owner/native reviewers can overrule for es/pt/nl/fr.
- nl and fr are written by Claude and must go to native review (same as the rest of the site; nl first). Terms to check: "gear reducer", "shaft-mounted", "torque arm", "rated power".
- Asset paths on language pages are root-relative (`/assets/products/…`, lesson 3); `verify-products.js` asserts zero `assets/` occurrences without a leading slash outside English.
- Footer language row and the flag buttons are patched in the new build code per page URL (lessons 1, 2). The `.footer-langs a` exclusion is kept in link rewriting.
- hreflang: each page lists the 5 variants plus `x-default` (English). Because slugs are shared and only the directory differs, the set is computed from the node, not hand-written.

## 10. Build, generated files and conventions

- `scripts/build-product-pages.js` is rewritten around the tree: load nodes, compute the published set, render hub, category and family pages for 5 languages, write the 5 search-index JSON files, write the sitemap entries. It keeps the existing approach of cloning the `about.html` shell through `cheerio`, and the existing language, schema and link-patching helpers.
- **Sitemap.** Today the Products URLs are in `sitemap.xml` by hand and `update-sitemap-lastmod.js` only refreshes dates. **[DECISION]** The build owns a delimited block in `sitemap.xml` (`<!-- products:start -->` … `<!-- products:end -->`) and regenerates it from the published set, so removed or newly published pages cannot drift. Dates still come from `update-sitemap-lastmod.js` in `build-all`, which must be able to map a node URL to its source (the data file plus the node's rows file) for `lastmod`. If the existing script's source map cannot express that, extend it with one entry rule for `products/` rather than a per-URL list.
- `llms.txt` and `llms-full.txt`: same approach, a delimited generated block listing published categories and families (name, URL, one line). The rest of those files stays hand-written.
- Line endings: generated HTML is written CRLF (as the current build does); the data and script files follow the existing files' endings; the new build asserts the output differs from a "no-op" run only where expected (lesson 5). `.htaccess` edits keep the file's existing endings.
- Stale output: when a node is renamed or unpublished, the build deletes generated product files that no longer belong to the published set (inside `products/` and the 4 language `products/` trees only, never anywhere else), and `verify-products.js` fails if orphan files exist. The old flat `ocr-rp-series-shaft-mounted-gear-reducers.html` files are removed in the same change as the 301.
- `npm run build-all` still ends with `update-sitemap-lastmod.js`; the new `import-spec-table` is a separate manual command (`npm run import-table -- <node> <file>`), not part of `build-all`.
- New assets under `assets/products/<family>/` (WebP + JPG fallback, generated from owner-supplied originals by a small `sharp` script, as `build-slide-images.js` does); originals are kept outside `assets/` or in a folder not referenced by pages.
- Branch and commit conventions per `CLAUDE.md` (`feat/…`, conventional commits).

## 11. Testing and acceptance

### 11.1 `verify-products.js` (extended; new sections `tree`, `search`)

Existing checks stay (nav on every page, hreflang, canonicals, no `data-i18n`, no prices, JSON-LD, links stay in the language directory), rewritten to iterate the published set rather than one hard-coded slug. New checks:

- **Tree:** every page's tree lists exactly the published nodes (no unpublished node, no missing one); hrefs are language-prefixed; `aria-current="page"` appears exactly once and points at the current node; the tree is a `div role="navigation"` with an `aria-label`, never a `<nav>`.
- **Breadcrumbs:** visible trail equals the `BreadcrumbList` JSON-LD names and URLs; the trail's last item is the page; every ancestor URL exists.
- **Populated-only:** for each node in the data file, published iff it has rows or live copy (or a published descendant); an unpublished node has no HTML file, no sitemap URL, no `llms*.txt` line, no search entry, no tree link. Includes a fixture node with empty `rows` that must stay absent.
- **i18n:** all 5 languages for every name/description/label/alt; no `assets/` path without a leading slash outside English; no English `alt` or `aria-label` text in es/pt/nl/fr (compare against the key table, and widen beyond a word list, lesson 20); every key used in markup has a value in all 5 languages.
- **Table:** row count in the HTML equals the data row count; every `data-*` value equals its visible cell; every row has an id and a Request-quote link with `item=<id>`; table has caption, `th scope="col"` and `th scope="row"`.
- **Sitemap parity:** the set of `/products/…` URLs in `sitemap.xml` equals the published set × 5 languages exactly; every hreflang alternate on a page is itself a sitemap URL (the sitemap has plain `<url>` entries, no `xhtml:link`, and stays that way); same parity for the `llms*.txt` block.
- **Search index:** for each language, JSON parses; contains every published category, family and every published model row; contains no unpublished node; every `u` resolves to a generated file (and the fragment to a real row id); size under budget (reported; fail above 100 KB).
- **Redirects:** `.htaccess` contains one `RedirectMatch 301` per old OCR URL with the right destination; (live `curl -I` is a manual post-deploy step, §11.4).
- **No tracking:** no `localStorage`, `document.cookie`, third-party fetch or analytics strings in generated Products pages or the inline scripts.
- **Contrast** tokens: the CSS used by Products pages does not use `--text-3` for text colour (grep on the generated CSS block).

### 11.2 Browser behaviour checks

Real-browser checks (webapp-testing / Playwright against a local static server, e.g. `python -m http.server` or `npx serve` from the repo root), run at **1280, 390 and 320 px with an explicit resize** (handoff lesson 13) and the language set en + one of es/pt/nl/fr (nl/fr first, longest labels):

- **Search:** no network request for the index on load; exactly one on first focus; typing `RP 50`, `rp50`, `RP-50` each shows the same model; `reduct`/`reductores` in the matching language; ↓ ↓ Enter opens the second result; Enter with no selection opens the top result; Esc closes and restores focus; the live region text changes; no horizontal overflow of the panel at 320 px; the result panel never covers the fixed nav in a way that blocks the input.
- **Filters:** with a fixture of ≥ 10 rows: select one enum value → count and visible rows change; a numeric min/max → correct rows; both together → intersection; Clear restores everything and disables itself; no-match state shows; reload with the query string restores the filter; Tab order is control → control → table; model column stays visible while scrolling the table sideways at 390 px.
- **No-JS:** with JavaScript disabled, the table shows every row, the tree is usable, and no broken or empty search widget is visible.
- **Layout:** measure widths with `getBoundingClientRect` (the in-app browser screenshots time out on long pages, handoff notes): no element wider than the viewport at 390/320 in all 5 languages; tree rail 240 px at 1280; tap targets ≥ 44 px on phone lists.
- **Accessibility:** automated axe-style run (or Lighthouse accessibility) on hub, one category and one family page; manual keyboard-only pass; contrast measured from computed styles.

### 11.3 Every new check must be seen failing (lessons 15, 21)

For each new oracle, the plan includes a mutation: break the thing it guards (delete a tree link, flip an `aria-current`, drop a language key, remove a sitemap URL, delete a row from the search index, change one `data-kw`, add `localStorage`) and show the check failing with a message that names that thing, after confirming the mutation actually changed the file. The check is also run against the current `master` (where the new sections do not apply or fail for the right reason) so the baseline is known. A check that was only ever green is not accepted.

### 11.4 Performance and post-deploy

- Lighthouse (mobile, throttled as in the handoff baseline) on `/products/`, a category and the family page, before and after: LCP and CLS no worse than the home/projects baselines (home 1.1 s, CLS 0); accessibility ≥ 96; SEO 100; best practices 100. JS added to the family page is ≤ ~5 KB minified before gzip; search JS ≤ ~4 KB.
- No new render-blocking request: the inline script is deferred to end of body, the index is fetched on focus only, fonts are the existing set.
- After deploy: `curl -I` the 5 old OCR URLs (301 + Location), the 5 new URLs (200), 3 unrelated pages (unchanged), `search-index.json` (200, `application/json`, charset), and fetch the live pages to check what Googlebot sees (lesson 18). Request indexing for the new URLs in Search Console (owner task).
